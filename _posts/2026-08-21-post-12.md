# PostgreSQL - Shutdown Modes

Official + Other Links:
&nbsp; &nbsp; &nbsp; &nbsp; |_ [Link 1](https://www.postgresql.org/docs/current/server-shutdown.html)
&nbsp; &nbsp; &nbsp; &nbsp; |_ [Link 2](https://www.postgresql.org/docs/current/app-pg-ctl.html)
&nbsp; &nbsp; &nbsp; &nbsp; |_ [Link 3](https://www.cybertec-postgresql.com/en/postgresql-shutdown-modes/)
&nbsp; &nbsp; &nbsp; &nbsp; |_ [Link 4](https://www.enterprisedb.com/blog/postgresql-shutdown)

PostgreSQL has 3 shutdown modes:

1. Smart
2. Fast
3. Immediate

Smart (SIGTERM) - This is the Smart Shutdown mode. After receiving SIGTERM, the server disallows new connections, but lets existing sessions end their work normally. It shuts down only after all of the sessions terminate.  If the server is in hot standby when a smart shutdown is requested, recovery and streaming replication will be stopped only after all regular sessions have terminated.

Fast (SIGINT) - This is the Fast Shutdown mode. The server disallows new connections and sends all existing server processes SIGTERM, which will cause them to abort their current transactions and exit promptly (All active transactions are rolled back and clients are forcibly disconnected.). It then waits for all server processes to exit and finally shuts down.

Immediate (SIGQUIT) - This is the Immediate Shutdown mode. The server will send SIGQUIT to all child processes and wait for them to terminate. If any do not terminate within 5 seconds, they will be sent SIGKILL. The supervisor server process exits as soon as all child processes have exited, without doing normal database shutdown processing. This will lead to recovery (by replaying the WAL log) upon next start-up. This is recommended only in emergencies.

Note: I have pasted official documentation definitions above, as they are crisp and explains sweetly + clearly.
If you wish to understand in more simpler way, you can read the link-3.

The default shutdown mode is 'fast'.
So, running simple `pg_ctl stop` automatically translates to `pg_ctl stop -m fast`.

IMPORTANT: Till postgresql 9.4, the default shutdown mode was 'smart' instead. From postgresql 9.5 and above, the default changed to 'fast'. Remember this, as if you work on old database versions, out of habit you can confuse the default shutdown mode. In such older versions, you can explicitly call full command `pg_ctl stop -m fast` rather relying on default.

## Do Not Use kill -9 to terminate postgres instance

I have seen many people make this mistake.

They wish to terminate the postgresql instance for some emergency reason (lets say postgres is not responding at all, and even the pg_ctl stop -m fast is not working), people then run `ps -ef|grep -i postgres` and kill -9 the POSTMASTER (postgres) process.

And if any remaining child processes, they kill them 1-by-1 by hand via kill -9 until all postgres processes are killed.

This is not good as it will lead the postgres server to be not able to release shared memory & semaphores.

Killing the PostgreSQL postmaster with SIGKILL is like cutting off a man's head while his hands, legs, and other body parts may continue moving. The head is gone, but the rest of the body does not necessarily stop immediately. Some parts may continue moving briefly or abnormally, while others may become stuck or remain in place because there is no longer a head (brain) coordinating them.

So what to do instead? For such emergency situations, the third shutdown mode, pg_ctl stop -m immediate, can be used. It terminates the PostgreSQL instance immediately, while still allowing PostgreSQL to coordinate the termination of its child processes.

To understand it simply: pg_ctl -m immediate first attempts to terminate the child processes (the body parts), force-kills any that do not terminate within 5 seconds, and then the postmaster (server) process exits (the head/brain exits in end), without performing normal database shutdown processing (like performing a final checkpoint). At the next database startup, PostgreSQL performs crash recovery by replaying the WAL, and once recovery is complete, the server starts accepting connections.

Conclusion: Do not use kill -9 to terminate a PostgreSQL instance. Instead, use PostgreSQL's immediate shutdown mode (pg_ctl stop -m immediate), which is designed to handle emergency shutdowns while coordinating the termination of PostgreSQL processes.

(Note: The terminology differs between PostgreSQL and Oracle. In Oracle, SHUTDOWN IMMEDIATE is a normal shutdown mode, whereas SHUTDOWN ABORT is used to terminate the Oracle instance abruptly. So, oracle people should be more careful while stopping postgresql database, as they can get confused and run pg_ctl -m immediate which is an abrupt database stop and not a clean shutdown. Hence, be careful!)

In the logs, we can clearly see that PostgreSQL recorded the **immediate shutdown request**:

```text
LOG:  received immediate shutdown request
LOG:  database system is shut down
```

Notice that there is **no final shutdown checkpoint** before the server stops. This is expected with `pg_ctl stop -m immediate`, because PostgreSQL skips the normal database shutdown processing and terminates the server processes without performing the usual final checkpoint.

When we start PostgreSQL again, the logs clearly show that the previous shutdown was not considered a clean shutdown:

```text
LOG:  database system was interrupted; last known up at ...
LOG:  database system was not properly shut down; automatic recovery in progress
```

PostgreSQL then starts WAL recovery as shown below.
In our test, there was essentially no WAL to replay, so recovery completed almost immediately.

```text
LOG:  redo starts at 0/88332C8
LOG:  redo done at 0/88332C8
```

And the message:

```text
invalid record length at 0/8833300: expected at least 24, got 0
```

This message "invalid record length at 0/8833300: expected at least 24, got 0" may initially look like WAL corruption. However, this is a normal consequence of crash recovery reaching the end of the WAL. Because the server was stopped immediately, PostgreSQL did not perform its normal shutdown processing. If WAL activity was in progress when the server processes were terminated, the latest WAL record may not have been fully written yet. During the subsequent recovery, PostgreSQL reaches that point, attempts to read the next WAL record, and finds an incomplete/absent record. PostgreSQL recognizes this as the end of valid WAL and stops redo at the previous valid position. This is why recovery completes successfully rather than reporting WAL corruption.

After recovery, PostgreSQL performed an **end-of-recovery checkpoint**:

```text
LOG:  checkpoint starting: end-of-recovery immediate wait
LOG:  checkpoint complete: wrote 3 buffers ...
```

Finally:

```text
LOG:  database system is ready to accept connections
```

So our experiment demonstrates the complete lifecycle of an immediate shutdown:

```text
pg_ctl stop -m immediate
        ↓
Immediate shutdown request logged
        ↓
No normal final shutdown checkpoint
        ↓
PostgreSQL processes terminate
        ↓
PostgreSQL starts again
        ↓
Automatic crash recovery
        ↓
WAL redo
        ↓
End-of-recovery checkpoint
        ↓
Ready to accept connections
```

## An interesting way to stop postgres database

I came across this approach in Link-4 (shared in blog beginning).
Its quite interesting and useful.

For a large and busy PostgreSQL database, shutdown can take considerable time because a clean shutdown performs a final checkpoint. If the database has a large number of dirty pages, flushing those pages to disk can make the shutdown take significantly longer.

So, a smart way is to perform manual checkpoint while the database is still running.
A checkpoint flushes dirty pages to disk. Automatic checkpoints do this as part of normal PostgreSQL operation, but here we are deliberately triggering one before shutdown so that most of the dirty pages are flushed while the database is still online.

This may temporarily increase I/O, just as an automatic checkpoint can, but the advantage is that the database remains available while this checkpoint work is being performed.

This is very useful if you want to Minimize Downtime.

That EDB Artile (link-4) suggests this to run:

`psql -c CHECKPOINT && pg_ctl stop -m fast`

The && ensures that pg_ctl stop -m fast runs only if the CHECKPOINT command succeeds.

Obviously, you can do them separately as well by manually connecting to database first and run a checkpoint.
And then run pg_ctl stop -m fast.
