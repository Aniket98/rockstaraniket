## Introduction

It is very difficult to enforce business rules regarding data integrity using Read Committed transactions because the view of the data is shifting with each statement, and even a single statement may not restrict itself to the statement's snapshot if a write conflict occurs.

What that last line means? "and even a single statement may not restrict itself to the statement's snapshot if a write conflict occurs"

Explaining with example:

```postgres
Transaction 1                  Transaction 2
--------------                 --------------
UPDATE account SET balance=...
                               SELECT/UPDATE same row
                               ↓
                               waits for TX1
TX1 COMMIT
                               ↓
                               PostgreSQL re-evaluate and continues using
                               the updated row version
```

So the second transaction's statement started with a particular snapshot, but after waiting for the concurrent transaction to finish, PostgreSQL can re-evaluate the target row using the newer committed version.

That's why the documentation says the statement “may not restrict itself to the statement's snapshot if a write conflict occurs.”

Moving on next.

Now, while a Repeatable Read transaction has a stable view of the data throughout its execution, there is a subtle issue with using MVCC snapshots for data consistency checks, involving something known as read/write conflicts. If one transaction writes data and a concurrent transaction attempts to read the same data (whether before or after the write), it cannot see the work of the other transaction. The reader then appears to have executed first regardless of which started first or which committed first. If that is as far as it goes, there is no problem, but if the reader also writes data which is read by a concurrent transaction there is now a transaction which appears to have run before either of the previously mentioned transactions. If the transaction which appears to have executed last actually commits first, it is very easy for a cycle to appear in a graph of the order of execution of the transactions. When such a cycle appears, integrity checks will not work correctly without some help.

(What does 'appear' mean here? Here, appear means the position of TX in the apparent dependency chain created due to RW Conflicts.
If you read the full post you will get the idea.)

As mentioned in [Official Section 13.2.3](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-SERIALIZABLE), Serializable transactions are just Repeatable Read transactions which add nonblocking monitoring for dangerous patterns of read/write conflicts. When a pattern is detected which could cause a cycle in the apparent order of execution, one of the transactions involved is rolled back to break the cycle.

#### What is SERIALIZATION Anomaly?

Question: But what if T2 wrote C based on some calcualtion based on B (but it was old snapshto), so its decision becamee wrong in reality as T1 modified B and commited.

Answer: Yes. **That can be a business-level problem, but it is not automatically a serialization anomaly.** This is exactly the distinction the PostgreSQL documentation is getting at.

Suppose:

```text
Initial:
A = 10
B = 20
C = 30

T1:
READ A
UPDATE B = 100
COMMIT

T2:
READ B = 20       ← old snapshot
UPDATE C = 20 + 30 = 50
COMMIT
```

If T2's snapshot was established before T1 committed, T2 legitimately sees `B = 20`.

Now the important question is:

> Can the final result be explained by **some serial execution**?

If the answer is yes, there is no serialization anomaly.

Here, the concurrent execution can be viewed as:

```text
T2 → T1
```

because T2's calculation used the old value of B, then T1 changed B.

So although **T2's decision may be undesirable from your business perspective**, it is still explainable by the serial order `T2 → T1`.

The real problem appears when you get a cycle such as:

```text
T1 →rw T2
T2 →rw T3
T3 →rw T1
```

Then **no serial ordering can explain the result**.

So remember:

> **“T2 made a decision using stale data” ≠ automatically “serialization anomaly.”**

A serialization anomaly requires that the **combined result cannot be explained by any serial ordering of the transactions**.


#### Whats a rw conflict, what is the conflict in that?

If T1 writes a version of some object, and T2 reads the previous version of that object, then T1 appears to have executed after T2, because T2 did not see its update. These are referred as rw-conflicts.

The word **“conflict”** is the confusing part. An `rw-conflict` does **not necessarily mean a transaction is blocked or gets an error**.

It means:

> One transaction **reads** data while another concurrent transaction **writes** that same data, and the reader's snapshot does not see that write.

Example:

```text
Initial: B = 20

T1: UPDATE B = 100
    (not committed yet)

T2: SELECT B
    → sees B = 20
```

Here:

```text
T2 →rw T1
```

To remember easily: T_read  ──rw──>  T_write
So the transaction that reads is on the left, and the transaction that writes the version that makes that read obsolete is on the right.

Why is this called a conflict?

Because the two operations concern the **same data item**, but they see different versions:

```text
T1 wants to write → B = 100
T2 reads          → B = 20
```

There is no blocking. There is no error. Nothing necessarily goes wrong.

The “conflict” becomes important for **serialization reasoning** because the database has to determine the logical ordering of these transactions while trying to find a valid serial order of execution.

In this example, because T2 did not see T1's write, the dependency is treated as:

```text
T2 →rw T1
```

meaning:

> **T2 must logically precede T1 in a serial interpretation.**

And one such dependency is perfectly fine. The problem is when several such dependencies form a cycle.



#### Whats the serialization cycle?

Let's build the 3-transaction case slowly. The key is to use **rw-dependencies**, because those are the interesting ones for Serializable Snapshot Isolation.

Suppose there are three pieces of data:

```text
A = 10
B = 10
C = 10
```

Now:

```text
T1: reads A, then writes B
T2: reads B, then writes C
T3: reads C, then writes A
```

So the actual operations are:

```text
T1: READ A ─────────→ WRITE B
T2:             READ B ─────────→ WRITE C
T3:                         READ C ─────────→ WRITE A
```

Because these transactions are concurrent and use snapshots, each reader can fail to see the concurrent writer's change.

Therefore we get three **rw-dependencies**:

```text
T1 ──rw──> T2
T2 ──rw──> T3
T3 ──rw──> T1
```

Which forms a cycle:

```text
        T1
       ↙  ↘
      T3 ← T2
```

Or more simply:

```text
T1 → T2 → T3 → T1
```

Now notice the problem: there is **no serial order** that can satisfy all three dependencies.

If you say:

```text
T1 → T2 → T3
```

then the `T3 → T1` dependency is violated.

If you start with T3:

```text
T3 → T1 → T2
```

then `T2 → T3` is violated.

And so on.

That is the **serialization cycle**.

One important correction to keep in mind from our earlier discussion: the `→` here is **not simply “T1 committed before T2.”** It represents a **read/write dependency** created by concurrent execution and snapshot visibility.

This is why PostgreSQL's `SERIALIZABLE` isolation cares particularly about **rw-dependency chains**: certain combinations can form a cycle even though each transaction individually sees a perfectly valid snapshot.


#### Discovering Possibilities

Suppose there are 3 rows A, B, C with initial values 10.20,30 respectively.
Now, 3 Transactions BEGIN in Repeatable Read Mode and run concurrently.

```
A = 10
	T1 --> reads A, updates A = 20
B = 20
	T2 --> reads A, updates B = A + B = 10 (old) + 20 = 30
C = 30
	T3 --> reads B, updates C = B + C = 20 (old) + 30 = 50

Now, all 3 Commit. The all 3 commit will go success as all three are updating different rows and also because they are in repeatable read, not serializable transaction isolation.

Now, trying to find a serial order that can explain the final result of :

A = 20
B = 30
C = 50

Serial Order Execution Possibilities: 

Possibility 1: T1 commits first and A becomes 20 --> Then, T2 commit cannot explain the B value update to 30 (because since T1 committed, B should have been B = A (new) + B (old) = 20 + 20 = 40.)

Possibility 2: T1 commits first and A becomes 20 --> Then, T3 commits, and updates C to 50. This is fine as B is not yet updated. --> Then, T2 commits and updates B to 30 which is wrong as already explained in Possibility 1.

Possibility 3: T2 commits first, updates B = 30 --> T1 commits, updates A = 20 --> T3 commits, updates C = 50, which becomes wrong as the sum should have been C = B (new) + C (old) = 30 + 30 = 60.

Possibility 4: T2 commits first, updates B = 30 --> T3 commits, updates C = 50, which is wrong as already explained in Possibility 4.

Possibility 5: T3 commits first, updates C = 50 --> T1 commits, updates A = 20 --> T2 commits, B = 30, which is wrong as already explained in Possibility 1.

Possibility 6: T3 commits first, updates C = 50 --> T2 commits, updates B = 30, which is valid. --> T1 commits, updates A = 20.
```

So, Possibility 6 is our solution, which shows that the serial order T3 → T2 → T1 produces the same final result as the concurrent execution of the three transactions. Hence, the three transactions are serializable.

Now, whhat additional dependency would we need to add to this example to make T3 → T2 → T1 become a cycle?.
In above example, T3 was dependent on T2, which in turn was dependent on T1, but T1 was not dependent on anyone.

So, if we make T1 dependent on either T2 or T3, then it creates a cycle.
Basically, if one or more nodes in a chain, gets dependent on one or more nodes in reverse direction of chain, then some form of cycle is confirmed to be created, which which makes the SERIAL ORDER Execution impossible that explains the final result of concurrent transactions execution.

Basically, if a dependency is created from a later node back to an earlier node in the chain, a cycle is created.

For example:


## How to Enforce Consistency

### 1. Enforcing Consistency with Serializable Transactions

If the Serializable transaction isolation level is used for all writes and for all reads which need a consistent view of the data, no other effort is required to ensure consistency. Software from other environments which is written to use serializable transactions to ensure consistency should “just work” in this regard in PostgreSQL.

When using this technique, it will avoid creating an unnecessary burden for application programmers if the application software goes through a framework which automatically retries transactions which are rolled back with a serialization failure. It may be a good idea to set default_transaction_isolation to serializable. It would also be wise to take some action to ensure that no other transaction isolation level is used, either inadvertently or to subvert integrity checks, through checks of the transaction isolation level in triggers.

See [Official Section 13.2.3](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-SERIALIZABLE) for performance suggestions.

Warning: Serializable Transactions and Data Replication
|_ This level of integrity protection using Serializable transactions does not yet extend to hot standby mode ([Section 26.4](https://www.postgresql.org/docs/current/hot-standby.html)) or logical replicas. Because of that, those using hot standby or logical replication may want to use Repeatable Read and explicit locking on the primary.

### 2. Enforcing Consistency with Explicit Blocking Locks

When non-serializable writes are possible, to ensure the current validity of a row and protect it against concurrent updates one must use SELECT FOR UPDATE, SELECT FOR SHARE, or an appropriate LOCK TABLE statement. (SELECT FOR UPDATE and SELECT FOR SHARE lock just the returned rows against concurrent updates, while LOCK TABLE locks the whole table.) This should be taken into account when porting applications to PostgreSQL from other environments.

Also of note to those converting from other environments is the fact that SELECT FOR UPDATE does not ensure that a concurrent transaction will not update or delete a selected row. To do that in PostgreSQL you must actually update the row, even if no values need to be changed. SELECT FOR UPDATE temporarily blocks other transactions from acquiring the same lock or executing an UPDATE or DELETE which would affect the locked row, but once the transaction holding this lock commits or rolls back, a blocked transaction will proceed with the conflicting operation unless an actual UPDATE of the row was performed while the lock was held.

Global validity checks require extra thought under non-serializable MVCC. For example, a banking application might wish to check that the sum of all credits in one table equals the sum of debits in another table, when both tables are being actively updated. Comparing the results of two successive SELECT sum(...) commands will not work reliably in Read Committed mode, since the second query will likely include the results of transactions not counted by the first. Doing the two sums in a single repeatable read transaction will give an accurate picture of only the effects of transactions that committed before the repeatable read transaction started — but one might legitimately wonder whether the answer is still relevant by the time it is delivered. If the repeatable read transaction itself applied some changes before trying to make the consistency check, the usefulness of the check becomes even more debatable, since now it includes some but not all post-transaction-start changes. In such cases a careful person might wish to lock all tables needed for the check, in order to get an indisputable picture of current reality. A SHARE mode (or higher) lock guarantees that there are no uncommitted changes in the locked table, other than those of the current transaction.

Note also that if one is relying on explicit locking to prevent concurrent changes, one should either use Read Committed mode, or in Repeatable Read mode be careful to obtain locks before performing queries. A lock obtained by a repeatable read transaction guarantees that no other transactions modifying the table are still running, but if the snapshot seen by the transaction predates obtaining the lock, it might predate some now-committed changes in the table. A repeatable read transaction's snapshot is actually frozen at the start of its first query or data-modification command (SELECT, INSERT, UPDATE, DELETE, or MERGE), so it is possible to obtain locks explicitly before the snapshot is frozen.
