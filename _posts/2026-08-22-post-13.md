**What is ACID?**

A -> Atomic : results of a transaction are seen entirely or not at all within other transactions.
(A transaction need not appear atomic to itself.)
C -> Consistent : system-defined consistency constraints are enforced on the results of transactions.
I -> Isolated : transactions are not affected by the behavior ofconcurrently-running transactions.
D -> Durable : once a transaction commits, its results will not belost regardless of subsequent failures.

(The above definitions are taken from Link-1. It's a postgresql pdf by Tom Lane in year 2000. Quite old, but have some good useful content explained in simple manner. Tom Lane is one of the top contributors in developing PostgreSQL. He is mainly responsible for the development of database query optimizer and planner, which decides how to run queries fast.)

**What is a Transaction?**

A transaction is a group of SQL commands whose results will be made visible to the rest of the system as a unit when the transaction commits --- or not at all, if the transaction aborts.

Transactions are expected to be atomic, consistent,isolated, and durable (acid).

And **what is Integrity Constraint?**

It often seems confusing whats the difference in 2 terms - 'consistency' (taken C from ACID) and 'integrity constraint'.

To get a clear difference and understand the relation between these 2 terms, we open Official PostgreSQL Glossary (Link-2).
And we get a good clear official defintions of various terms in PostgreSQL, which I am pasting below:

1. ACID : Atomicity, Consistency, Isolation, and Durability. This set of properties of database transactions is intended to guarantee validity in concurrent operation and even in event of errors, power failures, etc.

2. Atomicity: The property of a transaction that either all its operations complete as a single unit or none do. In addition, if a system failure occurs during the execution of a transaction, no partial results are visible after recovery. This is one of the ACID properties.

3. Consistency : The property that the data in the database is always in compliance with integrity constraints. Transactions may be allowed to violate some of the constraints transiently before it commits, but if such violations are not resolved by the time it commits, such a transaction is automatically rolled back. This is one of the ACID properties.

4. Durability : The assurance that once a transaction has been committed, the changes remain even after a system failure or crash. This is one of the ACID properties.

5. Contraint (Integrity Constraint): A restriction on the values of data allowed within a table, or in attributes of a domain.

6. Domain : A user-defined data type that is based on another underlying data type. It acts the same as the underlying type except for possibly restricting the set of allowed values.

====> So, integrity constraints are data restrictions that exist in various parts of database like row values in table, columns (attributes), foreign keys, etc.
Basically these are DATA Restriction Rules that are spread all over the database.

Example of these integrity constraints:

1. Column values
   salary INT CHECK (salary > 0)

   → restricts the values allowed in the salary column must be greater than 0.

2. Table rows
   PRIMARY KEY (employee_id)

   → prevents two rows from having the same employee_id.

3. Foreign keys
   orders.product_id REFERENCES products.product_id

   → product_id in orders must exist in products.

Now, what is consistency? How it relates to these integrity constraints?

The consistency is a higher-level vision over all these integrity constraints. When a transaction completes all of its operations, it will leave the database in a state with modified data changes. If all those data changes made in database made by that transaction are in-compliance with all the integrity constraints spread all over the database, we say this "state" of database to be "consistent". And when a COMMIT is triggered, it will go in success.

So, the result of a transaction, can leave the database state in "consistent" or "inconsistent (not consistent)".
If the database state is consistent on transaction completion, the COMMIT triggered goes in success. Else if a transaction leaves the database violating an integrity constraint and the violation is not resolved before commit, the database state will be inconsistent, the PostgreSQL will not allow that transaction to successfully commit and hence the transaction will be ROLLBACKED.

The above test demonstrates an important concept behind the “Consistency” in ACID.

We created the primary key as DEFERRABLE. This means PostgreSQL allows the constraint to be deferred during transcation and checked later at COMMIT, rather than necessarily checking it immediately after every statement inside transaction.

In the first transaction, we did not defer the constraint, so the primary key constraint was checked normally. Both values (1 and 2) were unique, so the transaction committed successfully.

In the second transaction, we explicitly executed:

    SET CONSTRAINTS ALL DEFERRED;

This deferred the primary key constraint until the end of the transaction.

(The term 'defer' in english language means 'to delay something until a later time' - [Cambridge Dictionary](https://dictionary.cambridge.org/dictionary/english/defer).)

We then inserted another value of 1:

    INSERT INTO math VALUES (1);

Notice that PostgreSQL accepted the INSERT even though the table now temporarily contained duplicate values:

    1
    2
    1 (duplicate value)

At this point, the database state inside this transaction violates the primary key's integrity constraint. However, because the constraint was deferred, PostgreSQL allowed this temporary inconsistent state.

Remember what we read in Glossary - 'Consistency' : The property that the data in the database is always in compliance with integrity constraints. Transactions may be allowed to violate some of the constraints transiently before it commits, but if such violations are not resolved by the time it commits, such a transaction is automatically rolled back. This is one of the ACID properties.

We then attempted to COMMIT without fixing the duplicate:

    COMMIT;

PostgreSQL checked the deferred constraint and detected the violation:

    ERROR: duplicate key value violates unique constraint "math_pkey"

The transaction therefore could not successfully commit.
And hence was ROLLBACKED. You can see the psql prompt changed from `postgres=*#` to `postgres=#` meaning now we are outside the transaction.

Finally, when we queried the table again, the duplicate value was gone and the table contained only 2 values as shown below:

    1
    2

This demonstrates what PostgreSQL means when it says that a transaction may temporarily violate some constraints before it commits.

The important point is that the database may be temporarily inconsistent within a transaction when a constraint is deferrable, but a transaction cannot successfully commit while leaving such a constraint violation unresolved.

Therefore:

Integrity constraints define the rules for what data is considered valid.

Consistency is the higher-level property that the database state resulting from a successfully committed transaction complies with those integrity constraints.
