# Oracle - Learning to Use SQL\*Plus in Smart Way

Bibliography:
	|_ [SQL\*Plus & SQL Buffer Official Documentation](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqpug/SQL-Plus-basics.html)
	|_ [O'Reilly - SQL Buffer](https://www.oreilly.com/library/view/oracle-sql-plus-the/1565925785/ch02s05.html)
	|_ [History Command](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqpug/HISTORY.html)

In this post, I am writing the 2 main sections :

1. Managing SQL\*Plus History and Re-running the commands easily
2. Making the display output neat and clean

When I started learning oracle in beginning, few things really disturbed me.

One thing is that to run an old query, i had to re-type everything.
It felt frustrating, as I come from postgres or mysql background, where finding previous queries is as simple as pressing the Up and Down arrow keys and to re-run them simply press enter.

But in Oracle SQL\*Plus, I had to re-type everything again. 

Other thing was the display format when you run the SQL Queries. It does not look beautiful by default.
SQL\*Plus does not auto set a clean column length, line size or page size. It rather gives you the control to tell SQL\*Plus how to display the output format. Honestly, it feels more work, but you need to learn it in order to work in SQL\*Plus with a sane mind.

Note: There is a separate tool Oracle SQLcl which is much better and removes many headaches that I listed above with SQL\*Plus.
But we need to learn SQL\*Plus as well, as it is widely & still primarily used at many places.

# 1. Managing History in SQL\*Plus

We will start with learning how to manage history of commands ran in the SQL\*Plus and how to re-run them.

### The SQL Buffer

Login to the sqlplus normally.

```sql
sqlplus / as sysdba
```

Now, run some query:

```sql
SQL> SELECT instance_name, status FROM v$instance;

INSTANCE_NAME
------------------------------------------------
STATUS
------------------------------------
DBNAME
STARTED


SQL>
```

(Ignore the ugly output display of query that SQL\*Plus gave. We will learn to fix in next sections of post.)

Now, the question "How do I re-run the last query I ran?".
Before answering this, you need to understand 1 thing called "SQL Buffer".

The official documentation describes it as:

```text
4.1.1 The SQL Buffer

The SQL buffer stores the most recently entered SQL command or PL/SQL block (but not SQL*Plus commands). The command or block remains in the buffer until replaced by the next SQL command or PL/SQL block. You can view the buffer contents with the LIST command.

You can execute the command or block in the SQL buffer using the RUN or /(slash) commands. RUN displays the command or block in the buffer before executing it. /(slash) executes the command or block in the buffer without displaying it first. For information about editing a command or block stored in the buffer see About Editing Scripts in SQL*Plus Command-Line.

SQL*Plus does not store SQL*Plus commands, or the semicolon or slash characters you type to execute a command in the SQL buffer.
```

In short, the SQL Buffer is an internal memory area that stores the last entered SQL command.

Focus ---> Last Entered (Not Last Executed)

To show the current contents of the SQL Buffer, we can run:

LIST or L or l (smaller case L)

(I said smaller case L as well, just to remind you that SQL\*Plus commands are case in-sensitive. And typing smaller case L is usually very comfortable and fast. Ofcourse, smaller case 'list' will work same as well.)

And to execute what is currently stored in SQL Buffer, you can type:

Either RUN or run or r
OR /

RUN --> prints the command first, then executes it, & then prints result
/ --> does not print the command, only executes it, & then prints result

Note: The SQL Buffer does not store SQL*\Plus commands or the semicolon or slash characters you type to execute a command in the SQL buffer.

Now, let's answer our question "How do I re-run the last query I ran?".
And the answer is I need to execute the contents of the SQL Buffer as it is storing my last entered SQL.

And to execute it we do either RUN or / :
```sql
SQL> list
  1* SELECT instance_name, status FROM v$instance
SQL>
SQL> run
  1* SELECT instance_name, status FROM v$instance

INSTANCE_NAME
------------------------------------------------
STATUS
------------------------------------
DBNAME
STARTED


SQL> /

INSTANCE_NAME
------------------------------------------------
STATUS
------------------------------------
DBNAME
STARTED


SQL>
```

Remember I said : Focus ---> Last Entered (Not Last Executed)
Understand this point.

Let's understand with example.
I will type a half-written SQL Query and then press Ctrl+c to abandon it. Then, we will see what gets stored in SQL Buffer.

Currently, the SQL Buffer contains:
```sql
SQL> list
  1* SELECT instance_name, status FROM v$instance
SQL>
```

Now, I start typing next SQL Query but not complete it and cancel it in-between.
```sql
SQL> select status
  2  from^C

SQL> list
  1* select status
SQL>
```

Do you see that? The last enter i pressed was after 'status' in 1st line. And it considered as the last entered command and replaced the content of SQL Buffer with this latest command.

It did not store the line 2 'from' as I did not press enter in that. I abandoned the 2nd line using Ctrl+c.

Even though the SELECT statement was incomplete, it stored it. So, that's the point to understand, the SQL Buffer stores the last command entered (literally press entered) and not the last successfully executed command.

If I try to run now, obviously it will fail as the SQL Buffer contains incomplete/wrong SQL statement:
```sql
SQL> run
  1* select status
select status
            *
ERROR at line 1:
ORA-00923: FROM keyword not found where expected


SQL>
```

If I try to abandon the 1st line itself using Ctrl+c, then the SQL Buffer contents are not replaced as in 1st line itself it will not be able to read enter because Ctrl+c will come before pressing enter. Below is example:

```sql
SQL> list
  1* select status
SQL>
SQL> select something^C

SQL> list
  1* select status
SQL>
SQL>
SQL>
SQL> select something
  2  from
  3  some table
  4  where^C

SQL> list
  1  select something
  2  from
  3* some table
SQL>

```

What if nothing is stored in the SQL Buffer? And i try to see the contents of SQL Buffer.
Then, it will simply tell me 'No lines in SQL buffer', below is example :

```sql
oracle@localhost:~> sqlplus / as sysdba

SQL*Plus: Release 19.0.0.0.0 - Production on Mon Sep 7 08:16:10 2026
Version 19.3.0.0.0

Copyright (c) 1982, 2019, Oracle.  All rights reserved.


Connected to:
Oracle Database 19c Enterprise Edition Release 19.0.0.0.0 - Production
Version 19.3.0.0.0

SQL>
SQL> list
SP2-0223: No lines in SQL buffer.
SQL>
```

What if something is stored in SQL Buffer, but I want to clear it.
Then, you may type : CLEAR BUFFER or CLEAR BUFF

```sql
SQL> select status from v$instance;

STATUS
------------------------------------
STARTED

SQL> list
  1* select status from v$instance
SQL>
SQL> clear buffer
buffer cleared
SQL>
SQL> list
SP2-0223: No lines in SQL buffer.
SQL>
SQL>
SQL>
SQL>
SQL>
SQL> select instance_name from v$instance;

INSTANCE_NAME
------------------------------------------------
DBNAME

SQL> list
  1* select instance_name from v$instance
SQL>
SQL> clear buff
buffer cleared
SQL>
SQL> list
SP2-0223: No lines in SQL buffer.
SQL>
SQL>
```

Another useful thing to know is that if multi-line content is stored in the SQL Buffer, then you can see a specific line as well, rather typing 'list' to show all content. To see a specific line, just type line number. Example:

```sql
SQL> list
  1  select instance_name,
  2  status
  3  from
  4* v$instance
SQL>
SQL> 1
  1* select instance_name,
SQL> 3
  3* from
SQL> 2
  2* status
SQL> 4
  4* v$instance
SQL> 5
SP2-0226: Invalid line number
SQL> 6
SP2-0226: Invalid line number
SQL>
```

If you enter a line number greater than what is stored in SQL Buffer, it will say 'Invalid line number' as shown above.

What if you wish to edit what is currently stored in the SQL Buffer.
For that, you can open the editor by typing 'ed' and it will open usually VI Editor (to set a specific editor like nano or vim, you can edit the variable \_EDITOR.)

Since, mostly VI editor is the usual default on linux, you can edit and save with :wq

Let's see example:
```
SQL> list
  1  select instance_name,
  2  status
  3  from
  4* v$instance
SQL>
SQL> ed
Wrote file afiedt.buf

  1  select version,
  2  status
  3  from
  4* v$instance
SQL>
SQL>
SQL> list
  1  select version,
  2  status
  3  from
  4* v$instance
SQL>
```

If you need to replace a specific line, you can do that with a shortcut as well.
Enter the line number and after that type the content that you wish to replace that line with.

Example:

```sql
SQL> list
  1  select instance_name,
  2  status
  3  from
  4* v$instance
SQL>
SQL> 2 version
SQL>
SQL> list
  1  select instance_name,
  2  version
  3  from
  4* v$instance
SQL>
```

There are other shortcuts as well to edit the SQL Buffer.
For now I am writing only this much as these are very practical and easy to learn & remember.

### Summary till now - SQL BUFFER

For managing the SQL Buffer:

| SQL\*Plus Command / Action | Purpose |
|---|---|
| `LIST` or `L` | List contents of SQL Buffer |
| `RUN` or `R` | Print command and execute contents of SQL Buffer |
| `/` | Don't print command; only execute contents of SQL Buffer |
| `CLEAR BUFFER` or `CLEAR BUFF` | Clear contents of SQL Buffer |
| Entering line number | Print specific line from SQL Buffer |
| Entering line number + content | Replace specific line in SQL Buffer |
| `ED` | Open editor to modify contents of SQL Buffer |

Next Question: "How to run the second last or older sql statements that I ran?"
Answer: You cannot run them using the SQL Buffer. As SQL Buffer only stores the last entered command only, and discards the old contents.

To solve this, we will need to enable History mode specifically in SQL\*Plus.
This leads to our next section.

### Enabling SQL\*Plus History

There is a SQL\*Plus command called 'HISTORY' or 'HIST'.
This can be used to enable and manage current session level history.

It stores the full history of all commands (unlike SQL buffer which only stores last command).
But 1 very big benefit is it also stores the SQL\*Plus commands history as well and not just SQL statements (which is not possible in the SQL Buffer).

The HISTORY command enables you to:

> List all entries in the command history list.
> Run an entry in the command history list.
> Edit an entry in the command history list.
> Delete an entry from the command history list.
> Clear all entries in the command history list.

To enable/disable history, run:

SET HISTORY ON
or
SET HIST ON

SET HISTORY OFF
or
SET HIST OFF

```sql
SET HISTORY ON
SET HISTORY OFF
```

You can verify the setting with:

SHOW HISTORY
or
SHOW HIST

```sql
SHOW HISTORY
```

Example:

```sql
SQL> set hist on
SQL>
SQL> show hist
history is ON and set to "100"
SQL>
SQL> set history off
SQL>
SQL> show history
history is OFF
SQL>
```

If you see above, the default history size is 100.
Meaning it can store upto 100 commands history.

To decrease/increase history size, you can type:

SET HISTORY <newsize>

Example:

```sql
SQL> show hist
history is ON and set to "100"
SQL> set hist 500
SQL> show hist
history is ON and set to "500"
SQL>
```

To view the current history list, you can run:

HISTORY
or
HIST
or
HISTORY LIST
or
HIST LIST

To run a specific entry, you can type:

HISTORY <entry number> RUN

Example:

```sql
SQL> hist
  1  select status from v$instance;
  2  select instance_name from v$instance;
  3  desc v$instance
  4  select sysdate from dual;
  5  desc dual
  6  select * from dual;

SQL> hist 4 run

SYSDATE
------------------
07-SEP-26

SQL>
```

To edit entry in history, run:

HISTORY <entry number> EDIT

This will open the default configured editor (typically VI Editor).

Note: It will not edit the actual history entry. It will edit and adds it as new entry at end of history list.
This edit command is more useful when you want to modify part of a long command without typing the entire command again.

After the modified command gets added to the list, you can execute using: HISTORY <line numnber> RUN.

Example:

```sql
SQL> hist
  1  select status from v$instance;
  2  select instance_name from v$instance;
  3  desc v$instance
  4  select sysdate from dual;
  5  desc dual
  6  select * from dual;

SQL> 
SQL> hist 2 edit
SQL> 
SQL> hist
  1  select status from v$instance;
  2  select instance_name from v$instance;
  3  desc v$instance
  4  select sysdate from dual;
  5  desc dual
  6  select * from dual;
  7  select i edited from v$instance;

```

As you can see above 7th new entry got added, but the 2nd entry remains intact.

To delete an entry, run:

HISTORY <line number> DELETE
	or
HISTORY <line number> DEL

After you delete an entry from the history list, the list is reordered to reflect the most recent changes.

Example:

```sql
SQL> hist
  1  select status from v$instance;
  2  select instance_name from v$instance;
  3  desc v$instance
  4  select sysdate from dual;
  5  desc dual
  6  select * from dual;
  7  select i edited from v$instance;

SQL>
SQL> hist 5 del
SQL> hist
  1  select status from v$instance;
  2  select instance_name from v$instance;
  3  desc v$instance
  4  select sysdate from dual;
  5  select * from dual;
  6  select i edited from v$instance;
```

The 5th entry deleted. And 6th and 7th entry moved upward in list.

To clear all entries in history, you can run:

HISTORY CLEAR

Example:

```sql
SQL> hist
  1  select status from v$instance;
  2  select instance_name from v$instance;
  3  desc v$instance
  4  select sysdate from dual;
  5  select * from dual;
  6  select i edited from v$instance;

SQL> hist clear
SQL> hist
SP2-1651: History list is empty.
SQL>
```

Note: History and the SQL Buffer Are Different. They are not same. Don't confuse.
This distinction is important.

### Summary - HISTORY Command

| SQL\*Plus Command | Purpose |
|---|---|
| `SET HISTORY ON/OFF` | Enable/disable history |
| `HISTORY` or `HISTORY LIST` | Show history |
| `HISTORY <entry number> RUN` | Run that entry |
| `HISTORY <entry number> EDIT` | Edit the entry and add the edited version as a new entry at the end of the history list |
| `HISTORY <entry number> DELETE` | Delete the entry |
| `HISTORY CLEAR` | Clear all history |

# 2. SQL\*Plus Output Formatting — Making SQL Queries Output Readable

When working with Oracle through SQL*Plus, the SQL statements output can become difficult to read because SQL*Plus has to decide how wide each column should be and how much data should fit on the screen.

We have to set manually how we wish to display the output.

### `SET LINESIZE`

`SET LINESIZE` controls the maximum width SQL\*Plus uses for a line of output.

You can run:

SET LINESIZE <new size>

To check, current linesize:

SHOW LINESIZE

Let's see a practical example.
Remember the ugly query we saw in start:

```sql
SQL> select instance_name,status from v$instance;

INSTANCE_NAME
------------------------------------------------
STATUS
------------------------------------
DBNAME
STARTED


SQL>
```

If we look carefully, its not using full width of screen.
It cut off and started new lines quite early.

So, if i let it print to more screen width, it should start looking pretty.

Let's run:

```sql
SQL> show linesize
linesize 80
SQL>
SQL> set linesize 200
SQL>
SQL> run
  1* select instance_name,status from v$instance

INSTANCE_NAME                                    STATUS
------------------------------------------------ ------------------------------------
DBNAME                                           STARTED

SQL>
```

See? It looks readable now.
Simple right.

Now, the linesize is set, I dont need to change it again for future sql statements, as i let it utilize much better screen width.

Although, if we look even more carefully, we can see the column width is taking a lot extra space.
If we have many columns, we will simply waste the total screen width.

Let's try to add more columns.

```sql
SQL> select instance_name,status,version,startup_time from v$instance;

INSTANCE_NAME                                    STATUS                               VERSION                                             STARTUP_TIME
------------------------------------------------ ------------------------------------ --------------------------------------------------- ------------------
DBNAME                                           STARTED                              19.0.0.0.0                                          07-SEP-26

SQL>
```

Till now, it looks fine.
Let's add more columns.

```sql
SQL> select instance_name,status,version,startup_time,instance_mode,database_status from v$instance;

INSTANCE_NAME                                    STATUS                               VERSION                                             STARTUP_TIME       INSTANCE_MODE
------------------------------------------------ ------------------------------------ --------------------------------------------------- ------------------ ---------------------------------
DATABASE_STATUS
---------------------------------------------------
DBNAME                                           STARTED                              19.0.0.0.0                                          07-SEP-26          REGULAR
ACTIVE


SQL>
```

Now output is getting mixed up as the total screen width is not enough.
Each column width is unnecessarily extra and its wasting space.

We fix column width next.

### `COLUMN ... FORMAT`

To set a column width, give the column name and the format type & size:

```sql
COLUMN column_name FORMAT format
```

For text columns, we commonly use the `A` format.

For example:

```sql
COLUMN name FORMAT A25
```

Here:

* `COLUMN name` — tells SQL*Plus which column to format.
* `FORMAT` — tells SQL*Plus how to display it.
* `A25` — display the text using a width of 25 characters.

For example:

```sql
COLUMN instance_name FORMAT A15
```

`A` means **alphanumeric/text**, and `25` means a display width of 25 characters.

Important: this does **not** change the database column or its datatype. It only changes how SQL\*Plus displays the result.

Let's fix our query now.

```sql
SQL> select instance_name,status,version,startup_time,instance_mode,database_status from v$instance;

INSTANCE_NAME                                    STATUS                               VERSION                                             STARTUP_TIME       INSTANCE_MODE
------------------------------------------------ ------------------------------------ --------------------------------------------------- ------------------ ---------------------------------
DATABASE_STATUS
---------------------------------------------------
DBNAME                                           STARTED                              19.0.0.0.0                                          07-SEP-26          REGULAR
ACTIVE


SQL>
SQL> column instance_name format A20
SQL> column status format A15
SQL> column version format A20
SQL> column instance_mode format A15
SQL> column database_status format A20
SQL>
SQL> l
  1* select instance_name,status,version,startup_time,instance_mode,database_status from v$instance
SQL> run
  1* select instance_name,status,version,startup_time,instance_mode,database_status from v$instance

INSTANCE_NAME        STATUS          VERSION              STARTUP_TIME       INSTANCE_MODE   DATABASE_STATUS
-------------------- --------------- -------------------- ------------------ --------------- --------------------
DBNAME               STARTED         19.0.0.0.0           07-SEP-26          REGULAR         ACTIVE

SQL>
```

See how we have now fitted our columns within the total screen width.
It looks much better and readable now.

I know this feels painful to think do I need to this for all queries.

The settings are session consistent.
So, setting enough linesize usually helps to utilize total screen width, which can easily fit large sized columns as well. 

But if the number of columns increase, you need to fit the large columns.
In such cases, look carefully at your screen and identify the problematic column and set its column width.
No need to set column width for all columns. Only fix problematic column.

But yes, it feels painful to fix the output display.

I have seen Oracle DBAs, they usually store display formatting commands along with the SQL command.
Then they simply copy paste the whole block at once to get a neat output.

The format value can be:

A20       ---> Text/alphanumeric, width 20

9         ---> Digit position
9999      ---> Number, 4 digit positions
0         ---> Zero/required digit position
99.99     ---> Number with 2 decimal places
999,999   ---> Number with comma grouping
$9999.99  ---> Currency symbol
B9999     ---> Blank zero value
MI        ---> Minus sign for negative numbers
PR        ---> Negative number shown in < >
EEEE      ---> Scientific notation

D         ---> Decimal character
G         ---> Group separator
L         ---> Local currency symbol
C         ---> ISO currency symbol
S         ---> Plus/minus sign
V         ---> Multiply by 10^n
RN        ---> Roman numeral

DATE      ---> Date format model

### Formatting numbers with `9`

Numbers use number format models rather than `A`.

For example:

```sql
COLUMN instance_number FORMAT 999999
```

Each `9` represents one available digit position.

So:

```text
999999
```

provides six digit positions.

For example, a value such as:

```text
123
```

fits comfortably inside the format.

You can also use decimal positions:

```sql
COLUMN value FORMAT 9999.99
```

This provides:

```text
9999.99
^^^^   ^^
 |      |
 |      +-- 2 decimal positions
 +--------- 4 positions before decimal
```

So a value such as:

```text
123.45
```

fits the format.

The formatting only affects display. It does not change the actual number stored in table.

---

### What happens when a number doesn't fit?

Suppose the actual value is:

```text
202444444444444
```

but you specify:

```sql
COLUMN size FORMAT 9999
```

There aren't enough digit positions to display the number.

SQL\*Plus will show `#` characters instead of silently displaying an incorrect or truncated number.

For example:

```text
###############
```

This means the value doesn't fit the display format.

It does **not** mean that the actual value consists of `#` characters.

The solution is to increase the format width:

```sql
COLUMN size FORMAT 999999999999999
```

Again, formatting controls presentation, not the underlying value.

### Putting the formatting together

Suppose we want to inspect some information from `V$INSTANCE`.

Instead of letting SQL\*Plus choose inconvenient widths, we can configure the display:

```sql
SET LINESIZE 150
SET PAGESIZE 100

COLUMN instance_name   FORMAT A15
COLUMN host_name       FORMAT A20
COLUMN version         FORMAT A12
COLUMN startup_time    FORMAT A18
COLUMN status           FORMAT A10

SELECT instance_name,
       host_name,
       version,
       startup_time,
       status
FROM v$instance;
```

The important distinction is:

```text
SET LINESIZE
    ↓
Controls the overall report width

SET PAGESIZE
    ↓
Controls the page length

COLUMN ... FORMAT
    ↓
Controls an individual column's display
```

---

### You don't need to format every column

You don't have to specify a format for every column in a query.

Only set column width for the columns which are causing display problems.

SQL\*Plus continues using its normal formatting for the other columns.
This is useful when only a few columns are causing an output problem.

---

The key principle:

**SQL\*Plus formatting changes how Oracle query results are displayed; it does not change the underlying database values.**

### Summary - SQL\*Plus Display Formmatting

| SQL\*Plus Command | Purpose |
|---|---|
| `SHOW LINESIZE` | Show the current line size |
| `SET LINESIZE <new size>` | Set the output line width |
| `SHOW PAGESIZE` | Show the current page size |
| `SET PAGESIZE <new size>` | Set the number of lines per page |
| `COLUMN column_name FORMAT format_value` | Set the display format for a column |

| SQL\*Plus Command / Action | Purpose |
|---|---|
| `LIST` or `L` | List contents of SQL Buffer |
| `RUN` or `R` | Print command and execute contents of SQL Buffer |
| `/` | Don't print command; only execute contents of SQL Buffer |
| `CLEAR BUFFER` or `CLEAR BUFF` | Clear contents of SQL Buffer |
| Entering line number | Print specific line from SQL Buffer |
| Entering line number + content | Replace specific line in SQL Buffer |
| `ED` | Open editor to modify contents of SQL Buffer |

Summary - The HISTORY Command:

| SQL\*Plus Command | Purpose |
|---|---|
| `SET HISTORY ON/OFF` | Enable/disable history |
| `HISTORY` or `HISTORY LIST` | Show history |
| `HISTORY <entry number> RUN` | Run that entry |
| `HISTORY <entry number> EDIT` | Edit the entry and add the edited version as a new entry at the end of the history list |
| `HISTORY <entry number> DELETE` | Delete the entry |
| `HISTORY CLEAR` | Clear all history |
