### A Surgery on - The Central Inventory (oraInventory)

The directory which is called "oraInventory" stores an inventory of all Oracle software installed on the system.

Focus here: The oraInventory is a "DIRECTORY" !!
Oracle refers to this directory itself as the Central Inventory.

This directory `oraInventory` contains files that make up that inventory, including an important file: `ContentsXML/inventory.xml`

This file `inventory.xml' contains inventory data (such as registered Oracle Homes).

Some additional files may appear inside the oraInventory directory, only during certain operations and are transient in nature. Because they are created only when needed, they may not exist permanently inside the oraInventory directory.

For example, lock-related files may appear during software installation or patching to prevent multiple processes from updating the inventory simultaneously.

1) ContentsXML

***

ContentsXML is a directory inside the Central Inventory directory that stores core inventory metadata.

This is one of the most important directories inside oraInventory, because it contains XML files that describe:

-- Which Oracle Homes are registered on the system
-- Which Oracle components are installed
-- Metadata related to patches
-- Other information used by Oracle tools such as OUI and OPatch

Inventory information is stored in Extensible Markup Language (XML) format. The XML format enables easier diagnosis of problems and faster loading of data.

Some important files inside ContentsXML include:
		
``` bash
[dir] oraInventory
		|_ [dir] ContentsXML/ — stores core inventory metadata
				|_ [file] inventory.xml — registered Oracle Homes
				|_ [file] comps.xml — installed components
				|_ [file] libs.xml — library metadata
				|_ [file] oui-patch.xml — patch-related metadata
```

As we can see each file is having .xml extension.

##### inventory.xml

Before we move further, here are XML Syntax – Quick Guidelines:
|_ Helpful Link: [W3Schools - XML](https://www.w3schools.com/xml/xml_syntax.asp)

```
#XML Syntax – Quick Guidelines

1. Must have ONE root element
   - All elements go inside a single parent

2. XML declaration (The XML prolog is optional. If it exists, it must come first in the document.)
   <?xml version="1.0" encoding="UTF-8"?>

   Note: The XML prolog does not have a closing tag! This is not an error. The prolog is not a part of the XML document.

3. Every tag must have a closing tag
   <tag>value</tag>

   You can also use a so called self-closing tag: <tag />

4. Tags are CASE-SENSITIVE
   <Name> is not equal to <name>

5. Proper nesting is required
   Correct: <a><b></b></a>
   Wrong: <a><b></a></b>

6. Attribute values must be quoted
   <tag attr="value">

7. Special characters must use entities
   < → &lt;
   > → &gt;
   & → &amp;
   ' → &apos;
   " → &quot;

8. Comments syntax
   <!-- comment -->

9. Whitespace is preserved
   (spaces are not ignored)

10. New lines stored as LF

   Windows applications store a new line as: carriage return and line feed (CR+LF).
   Unix and Mac OSX use LF.
   Old Mac systems use CR.
   XML stores a new line as LF.

11. XML documents that conform to the syntax rules above are said to be "Well Formed" XML documents.
```

Opening the `inventory.xml`, we see:

``` bash
oracle@10:/u01/app/oraInventory/ContentsXML> cat inventory.xml
<?xml version="1.0" standalone="yes" ?>
<!-- Copyright (c) 1999, 2026, Oracle and/or its affiliates.
All rights reserved. -->
<!-- Do not modify the contents of this file by hand. -->
<INVENTORY>
<VERSION_INFO>
   <SAVED_WITH>12.2.0.7.0</SAVED_WITH>
   <MINIMUM_VER>2.1.0.6.0</MINIMUM_VER>
</VERSION_INFO>
<HOME_LIST>
<HOME NAME="OraClient19Home1" LOC="/u01/app/oracle/product/19.0.0/client_1" TYPE="O" IDX="1"/>
<HOME NAME="OraDB19Home1" LOC="/u01/app/oracle/product/19.0.0/db_1" TYPE="O" IDX="2"/>
</HOME_LIST>
<COMPOSITEHOME_LIST>
</COMPOSITEHOME_LIST>
</INVENTORY>
oracle@10:/u01/app/oraInventory/ContentsXML>
```

The file begins with an XML Declaration (called XML prolog): `<?xml version="1.0" standalone="yes" ?>`

version="1.0" → Says the file follows XML version 1.0 rules.

standalone="yes/no" → In an XML prolog, the standalone attribute is an optional part of the XML declaration that tells the parser whether the document depends on external resources, such as an external Document Type Definition (DTD).

+ standalone="yes": Indicates the document is self-contained. The parser assumes all necessary declarations (like entities or attribute defaults) are contained within the internal subset of the document.
+ standalone="no": This is the default value. It indicates that the document may rely on information from an external source, such as an external DTD, to be processed correctly.

Then, we see the XML elements:

```
What is an XML Element?
An XML element is everything from (including) the element's start tag to (including) the element's end tag.
```

`<INVENTORY>` → Root element. Everything in this file sits inside it.
`<VERSION_INFO>` → Version details of the inventory
`<SAVED_WITH>` → Version of Oracle tools (OUI, OPatch, etc) that last updated this inventory.
`<MINIMUM_VER>` → Minimum version of Oracle tools required to read/use this inventory.
`<HOME_LIST>` → Contains all registered Oracle Homes on the system.

`<HOME ... />` → Each entry represents one Oracle Home.
[Notice: This HOME is a self-closing XML tag]

Attributes in `<HOME ... />` tag:

NAME: logical name of the Oracle Home
LOC: actual filesystem path (this is the real location)
TYPE: type of home (commonly O = Oracle Home)
IDX: internal index (unique ID inside inventory)

`<COMPOSITEHOME_LIST>` → Used for special/combined homes (rare in simple setups).

##### comps.xml - Components File

The `comps.xml` stores information about Oracle components & patchsets installed in the Oracle Home.
While inventory.xml tracks Oracle Homes, comps.xml goes one level deeper and tracks what is installed inside those homes.
|_ [Official Old Link](https://docs.oracle.com/cd/B16240_01/doc/em.102/b16227/oui3_manage_oracle_homes.htm#CHDICBGF)

This file contains the details about third party applications like Java Runtime Environment (JRE) required by different Java-based Oracle tools and components. In addition, it also contains details of all the components as well as patchsets or interim patches installed in the Oracle home.

For a sample of the components file refer to section "[Sample Components File](https://docs.oracle.com/cd/B16240_01/doc/em.102/b16227/d_oui_appendix.htm#BEHHFDDD)".

The comps.xml begins with XML prolog (which we have already discussed).

Next, XML Elements:-

`<PRD_LIST>` → Root element of the file.
`<TL_LIST>` → Typically used for top-level (TL) product information.
`<COMP_LIST>` → Intended to store details about installed components.
`<PATCHSET_UPDATE_LIST>` → Used to track patch set updates applied to components.

##### libs.xml

The libs.xml is an internal-use file used by Oracle Universal Installer and related tools, and it does not typically contain information relevant for regular database administration.

Oracle does not provide detailed public documentation for libs.xml. Based on its structure and placement in the Central Inventory, it appears to be used internally by Oracle Universal Installer for managing installer logic such as queries, dialogs, and actions.

oraInventory (Central Inventory) - libs.xml:
``` bash
oracle@10:/u01/app/oraInventory/ContentsXML> cat libs.xml
<?xml version="1.0" standalone="yes" ?>
<!-- Copyright (c) 1999, 2026, Oracle and/or its affiliates.
All rights reserved. -->
<!-- Do not modify the contents of this file by hand. -->
<LIB_LIST>
<QUERY_LIST>
</QUERY_LIST>
<DIALOG_LIST>
</DIALOG_LIST>
<ACTION_LIST>
</ACTION_LIST>
</LIB_LIST>
oracle@10:/u01/app/oraInventory/ContentsXML>
```

The file begins with XML prolog.

Next, XML Elements:

The exact purpose of these XML Elements is not officially documented. Based on their names, they appear to relate to internal installer logic such as checks (queries), user interactions (dialogs), and operations (actions).

`<LIB_LIST>`
Root element of the file.

`<QUERY_LIST>`
Likely holds definitions the installer uses to check conditions
(example: network checks, os level checks, file system checks, etc)

`<DIALOG_LIST>`
Likely related to installer UI interactions
(example: prompts, screens, or inputs shown during installation)

`<ACTION_LIST>`
Likely defines operations the installer can execute
(example: file copy/move/delete operations, os level commands, run scripts, permission/ACL handling, etc)

The above is an interpretation of what these XML elements might represent based on their names and structure, as no official Oracle documentation explicitly defines their purpose.

Also, does the term 'libs' in the file name libs.xml mean 'libraries'? The file name "libs.xml" most likely refers “internal libraries” (a collection of reusable definitions) used internally by the Oracle installer, but again there is no Official Documenation to support this.

##### oui-patch.xml

The oui-patch.xml stores information about patches applied to Oracle Homes.

Before we go furhter, some basic information about Oracle Patches. The following termns are commonly used:

 1) Reactive Patches --> These are patches created to fix a specific issue or bug when it is encountered. They are typically released on demand and are often referred to as 'interim' patches (Historically known as “one-off” patches).

 2) Proactive Patches (patch bundles) --> These are regularly released patch bundles that include fixes for multiple known issues, along with security updates and improvements. These are commonly known as Release Updates (RU) and Monthly Recommended Patches (MRPs).

[Official Link for Oracle Patches](https://docs.oracle.com/en/database/oracle/oracle-database/26/dbptc/index.html#GUID-A831852D-28AC-4C82-A5D4-5051C14BF4D2)

Additional note: What one-off name means?
```
One-off

one = single  
off = separate / not part of a series

So, one-off means:
something done once, as a single and separate item.

In Oracle:
A one-off patch = a single patch created to fix one specific issue.
```

The one-off is an English term.
You can see the dictionary meanings as well:

1. [Cambridge Dictionary](https://dictionary.cambridge.org/dictionary/english/one-off) says: one-off --> something that happens or is made or done only once.
2. [Oxford Dictionary](https://www.oxfordlearnersdictionaries.com/definition/english/one-off_1) says: one-off --> a thing that is made or that happens only once and not regularly
3. [Wikipedia](https://en.wikipedia.org/wiki/One-off) says: one-off -->  something made or occurring only once, independent of any pattern.

2) logs

***

The logs directory inside oraInventory stores log files generated during Oracle installation, patching, and configuration activities performed by OUI (Oracle Universal Installer).

It helps track what happened during each operation and is mainly used for troubleshooting and auditing installation steps.

1) Grouped logs

Some logs are grouped into a timestamp-based sub-directory under logs/.

Example:
logs/InstallActionsYYYY-MM-DD_HH-MM-SS/

Inside this directory, you may find:

installActions*.log → main execution flow log  
installActions*.out → standard output messages  
installActions*.err → error messages  
installerPatchActions*.log → patch-related actions  
time*.log → timing details  

Difference in .log .out .err ? The file .log is the primary OUI-generated record, while .out and .err are raw execution streams captured during the proces (stdout and stderr repectively).

What is time*.log?

time*.log is a timing log file generated by OUI that records the "duration" of installation or patching steps, used for performance tracking and debugging slow phases of the process.

It helps identify which step took how much time.
It is mainly used for troubleshooting performance issues or slow installations.

2) Non-grouped logs (directly inside logs/)

Some logs are not placed in a separate sub-directory and are created directly under logs/, for example:

oraInstall*.log → installer runtime log  
silentInstall*.log → silent installation log  
installActions*.log → summary log for certain runs  
`*.err` / `*.out` → direct output/error logs for simple executions  
time*.log → timing details

Why backup is created?

The backup is generated automatically before OUI modifies inventory files. This ensures that changes made during installation or patching can be restored if required.

Each backup timestamp matches one OUI operation, so you can identify which change updated the inventory.

##### oui directory

The `oui` directory inside `oraInventory` is used by Oracle Universal Installer (OUI) to store installation source configuration metadata.

What “Source configuration metadata” means? It is the information (metadata) that tells the installer where the Oracle installation files come from and how to access them.

In above output, you can see: `<StgArea URL="/u01/software/client/install/../stage/products.xml" />`

Here, the Staging area is → `/u01/software/client/install/../stage/`
Source configuration → XML entry that tells OUI where that staging folder is.

The staging area is actual folder with Oracle installation media files.

Flow summary:

srcs.lst (source configuration)
        ↓
points to staging area (/stage/)
        ↓
staging area contains products.xml
        ↓
OUI reads products.xml to build installable product list

1) Source configuration (srcs.lst)

The `srcs.lst` file tells OUI where to look for installation media.

Example:

`<StgArea URL="/u01/software/client/.../stage/products.xml" />`

This means:
-- OUI reads `srcs.lst`
-- It gets the location of the staging area
-- It identifies `products.xml` as the entry point

2) Staging area (actual software location)

The staging area is the real directory on disk that contains Oracle installation media.

Example:
`/u01/software/client/.../stage/`

This directory contains:
-- products.xml
-- component definitions
-- installation files and metadata

So, the staging area is the actual source of installation files.

products.xml (inside staging area)

The `products.xml` file is part of the staging area and is provided with Oracle installation media.

It defines:
-- available Oracle products
-- components of each product
-- dependencies between components
-- installation structure and metadata

Important point for products.xml file:
-- It is NOT manually created or added by the user
-- It is automatically included when Oracle software is staged or extracted

##### oraInst.loc (Oracle Inventory Pointer File)

The `oraInst.loc` file is a configuration file used by Oracle Universal Installer (OUI) to locate the Central Inventory on a system.

It acts as a pointer that tells Oracle:
-- where the Central Inventory directory is located
-- which operating system group owns and manages the inventory

Example:
``` bash
10:~ # cat /etc/oraInst.loc
inventory_loc=/u01/app/oraInventory/
inst_group=oinstall
```

##### Locations of oraInst.loc

There are two primary locations associated with this file:

1) System-level location (primary reference used by Oracle)

This is the main file used by Oracle Universal Installer (OUI), OPatch, and other installation tools.

Path:
`/etc/oraInst.loc`

This file is the active system pointer that tells Oracle:
-- where the Central Inventory is located
-- which OS group owns the inventory

During most installation, upgrade, and patch operations, this is the file that is read first.

2) Central Inventory copy (inventory-level reference)

Path:
 /u01/app/oraInventory/oraInst.loc

This is a copy maintained within the Central Inventory itself.

Other point:

In addition, copies may also exist inside individual Oracle Homes. These are local copies created during installation by Oracle Universal Installer (OUI).

Example paths:
 /u01/app/oracle/product/19.0.0/db_1/oraInst.loc
 /u01/app/oracle/product/19.0.0/client_1/oraInst.loc

They appear inside each ORACLE_HOME and typically contain the same inventory pointer information as /etc/oraInst.loc.
